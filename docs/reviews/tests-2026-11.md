## 2. Причины медленных и нестабильных integration-тестов

### Проблемы тестов (чиним мы)

1. **Контейнер на каждый вызов `dbtest.New`.** За один `make test-int` стартует 138–148 контейнеров `postgres:17` (`pg/` ≈ 102, `jobs/` ≈ 36, `pjobs/` 9, dbtest 1). Старт + `initdb` + goose + миграция River ≈ 4 с на контейнер в тихой системе и 7–15 с под нагрузкой. Это ≈ 90% времени `make test-int`.
2. **Миграции на каждый тест** — goose и River прогоняются заново в каждом контейнере (там же, в `dbtest.New`).
3. **Контейнер на подтест.** `TestBackups_saveChosenTx`, `TestSyncs_*` и др. вызывают `domainRepoWith`/`newRepo` внутри `t.Run` → контейнер на строку таблицы. Рядом уже есть правильный шаблон (`syncEnv.fresh`, `txEnv.fresh`: один контейнер, новый пользователь на подтест) — но он применён не везде и держит изоляцию «по пользователю», а не «по базе».
4. **Фиксированные `time.Sleep` для негативных проверок** в `jobs/`: `sweep` 2 с + 1 с, `upload_race` 1 с + 2 с, `retry` 1 с, `jobs_integration` 3 × 1 с — ≈ 11 с «подождём, вдруг лишнее» вместо ожидания терминального состояния задачи. Плюс `Eventually` с таймаутом 30 с (`sync`, `purge_pending`, `upload_race`) — при поломке тест висит 30 с.
5. **Реальные задачи River** запускаются в большинстве `jobs/`-тестов; логика воркеров, которую можно проверить прямым вызовом `Work` с фейками, гоняется через очередь и БД.
6. **Нет изоляции на уровне базы.** Общие данные между подтестами разведены счётчиками пользователей (`userSeq`, `txUserSeq` — package-level mutable vars) и «аккуратностью». Если переключить тесты на общий контейнер как есть, River-клиенты разных тестов начнут забирать чужие задачи.
7. Порты: контейнеры берут случайные порты — коллизий нет. Общих данных между пакетами нет (контейнер на пакет-процесс).

### Проблемы Docker-окружения (не наши, но усугубляются нашими)

- Таймаут `docker.sock` на `inspect` контейнера (64 с) возникает, когда Docker Desktop захлёбывается от потока `create/start/rm`: падения были даже при `-p 1` (пакеты по очереди). Это не лечится в тестах, **но лечится снижением числа контейнеров 148 → 3 (по одному на пакет)**: Docker перестанет быть узким местом, и таймаут ожидаемо уйдёт.
- `TerminateContainer` в `t.Cleanup` каждого теста добавляет время на каждый тест (не замерялось отдельно). Уходит вместе с п. 1.
- Первый запуск после очистки образов тянет `postgres:17` — в замеры не входит (образ уже был).

Остаточный риск: если после перехода на контейнер-на-пакет падения останутся, то это окружение; в этом случае добавляем в `dbtest` одну повторную попытку старта контейнера (только старт, не тест) и фиксируем в PR. Решение — по факту замеров фазы 2.

### Предложенная схема изоляции

Один контейнер на пакет (`TestMain` → `dbtest.Run(m)`), внутри:
1. Контейнер стартует один раз, на нём создаётся база-шаблон `tmpl`, в неё один раз применяются goose + River.
2. `dbtest.New(t)` (сигнатура не меняется, ~140 вызовов не трогаем) делает `CREATE DATABASE t_<n> TEMPLATE tmpl` (≈ 50–100 мс), открывает пул на неё и в `t.Cleanup` закрывает пул и делает `DROP DATABASE ... WITH (FORCE)`.
3. База на тест → River-клиенты, `LISTEN/NOTIFY`, данные, счётчики id — изолированы полностью; `userSeq`/`txUserSeq` можно удалить; тесты можно запускать `t.Parallel()`.
4. Ограничить `MaxConns` пула (4), чтобы 100 соединений `max_connections` хватало при параллельных тестах.

Единственное хранилище состояния — одна package-level переменная в `dbtest` (контейнер и шаблон), с комментарием-исключением по правилу 9 CLAUDE.md. Тестовых швов в продакшен-коде не нужно.
